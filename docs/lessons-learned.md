# 经验记录

## 2026-03-29：依赖安全收口时要同时做“直接升级 + 依赖归类 + overrides”

### 问题

`xlsx` 替换掉之后，生产依赖审计里仍然有一批 `high`，来源并不完全相同：

- 一部分来自直接依赖过旧，如 `next`、`better-auth`、`wrangler`
- 一部分来自纯构建期依赖被放进了 `dependencies`
- 还有一部分来自暂时无法直接升级的传递依赖

### 处理方式

- 先升级直接依赖到当前兼容补丁版本
- 把只在 `tailwind.config.ts` 使用的 `@tailwindcss/typography` 挪到 `devDependencies`
- 用 `pnpm.overrides` 定向压住 audit 里仍命中的高危传递版本
- 每收一轮都重新跑 `type-check`、`lint`、`vitest`、`build` 和 `pnpm audit --prod`

### 经验

- 依赖安全不能只靠“升级几个包”，还要校正哪些包本来就不该算进生产依赖
- 对模板站这类仓库，`pnpm audit --prod` 比全量 audit 更接近真实上线暴露面
- 对传递依赖，优先用小范围 `overrides` 收口，通常比贸然升级一整串上游库更稳

### 踩坑记录

- **坑**: 只看 audit 总数，容易把“构建期包挂错位置”和“运行时真实高危”混在一起处理
- **避免方法**: 先用 `pnpm why <package>` 看路径，再决定是升级、挪依赖层级，还是加 override

## 2026-03-28：本地 D1 持久化要同时校对 schema、迁移和 seed

### 问题

为了让模板后台的设置和线索在本地跨重启保留，本轮补了本地 D1 的 migrate / seed / setup 流程。实际执行时，seed 报错：`table products has no column named images`。

### 处理方式

- 先用 `pnpm db:local:seed:dry` 验证生成的 SQL 全是 mock data，没有混入真实业务信息
- 再直接检查 `src/drizzle/schema.ts` 与 `src/drizzle/*.sql`，定位到 `products.images` 已写进 schema，但迁移里没有补这列
- 新增 `src/drizzle/0005_add_product_images.sql` 后重新执行本地 migrate / seed
- 最后直接读取 `.wrangler/state/v3/d1/miniflare-D1DatabaseObject/*.sqlite`，确认 `global_config`、`products`、`contacts`、`inquiries` 已真实落盘

### 经验

- 只看 TypeScript schema 不够，本地数据库初始化前必须同步核对 SQL migrations
- 模板仓库要把本地初始化命令和恢复说明写进 README / restore 文档，否则换机后很容易只恢复代码，不恢复本地数据层
- 涉及模板 seed 时，先跑 dry run 再落库，能更早发现真实数据混入或字段漂移

### 踩坑记录

- **坑**: 代码层已经新增字段，但历史迁移没补，最终只会在本地 seed 或恢复环境时暴露
- **避免方法**: 任何依赖本地数据库的模板改动，都至少做一次“迁移 + seed + 直接查库”的闭环验证

## 2026-03-20：架构切换后，测试也要同步对齐当前入口

### 问题

仓库完成 Next App Router + OpenNext 方案收口后，代码、依赖和测试没有同步按当前入口整理，导致：

- 安全收口完成后，仍有不应继续暴露的公开接口
- `vitest` 默认执行时，仍带着过期的入口假设
- E2E 直接依赖本地 3002 服务，未做显式开关

### 处理方式

- 删除不再属于当前发布方案的入口文件、路由目录和无人引用 helper
- 补一个统一错误响应 helper，避免继续把内部异常细节回给客户端
- 把产品接口测试改成直接测当前 Next Route Handler
- 将 E2E 改为显式通过 `RUN_API_E2E=true` 才执行

### 经验

- 架构切换时，代码、依赖、测试、伪接口要一起收口，不能只改部署入口
- 需要外部服务的 E2E 默认应关闭，避免把“环境没起”误报成“代码坏了”
- 公开 API 的错误结构应该集中封装，否则很容易在局部回归时重新泄漏内部信息

## 2026-03-20：模板项目要彻底切断废弃数据源

### 问题

模板站已经切到本地 mock 数据和 Cloudflare API，但仓库里仍残留旧 CMS 取数层与旧组件，导致 `build` 阶段继续打印外部抓取失败和数据库回退日志。

### 处理方式

- 将活跃页面改为直接读取现有的本地/D1 数据层
- 删除未被当前路由引用的旧 CMS 工具与旧组件
- 同步移除无用依赖，避免模板继续携带错误心智

### 经验

- 模板迁移不能只改入口页面，还要清掉残留的旧数据适配层
- 构建成功不代表数据链路干净，日志里的降级信息要继续追到源头
- 对于没有被当前路由使用的旧 CMS 组件，直接删除比继续兼容更稳

## 2026-03-13：线索归因与网站转化

### 问题

站点虽然能把来源信息带入邮件，但归因数据没有入库，后台也无法按线索状态管理。

### 处理方式

- 复用现有埋点加载逻辑
- 把归因字段写入数据库
- 把后台联系人页改造成统一线索中心

### 经验

- 表单提交应视为采集入口，一次采集，多处消费
- 只在前端触发转化事件而不落库，后续很难做人工核验与回传
- 后台状态字段要和“已读/已回复”这类流程字段分开

## 2026-03-12：清理告警时同步检查类型

### 问题

只看 `lint` 结果容易误判完成，很多遗留类型问题只有 `type-check` 才会暴露。

### 处理方式

- 清理告警时同步执行类型检查
- 在复杂表单处显式补足泛型
- 在遗留兼容层先收口宽松类型

### 经验

- 先让边界变清晰，再逐步推进强类型
- 一次任务不要顺手把不相关的历史类型问题全部摊开

## 2026-03-12：联系与询盘邮件接入

### 问题

公共表单通过了验证，但没有真正发出通知邮件。

### 处理方式

- 将联系表单与询盘表单接到邮件服务封装
- 在邮件中附带访客轨迹、来源与基础地理信息

### 经验

- 线上表单命名差异要在服务端兼容
- 归因信息应优先读追踪参数，再回退到来源地址
